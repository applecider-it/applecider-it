## 全般的な設計思想

### 基本的な想定

- ハイブリッドMPAで安く早く作る。ランニングコストも安く済ませる。

- アプリ化の要望があった時はPWAで安く済ませる。JSONとアイコンを用意するだけ。start_urlを工夫すれば、アプリっぽい初期表示も作れる。一般ユーザーにとっては、PWAもCapacitorによるアプリも違いがわからないと思います。技術的には、中身はほとんど同じ。PWAだと、アプリの更新が不要。審査も不要。手数料もない。サーバーサイドのバージョン管理をしないでいい。

- Nodeは、開発環境、WebSocketサーバーのみを想定。

- Goは、高速なWebSocketサーバーのみを想定。

- ビジネスロジックは、カテゴリーごとにディレクトリをわけたサービスクラスで整理する。シンプルだけど見通しがいい構成。

- カメラ、GPSみたいなネイティブ機能は、JSで。モバイルだと加速度センサーの取得も可能。

- ゲーム関連などは別枠でUnity。この場合は、アプリでも仕方がない。

### ハイブリッドMPA

- ハイブリッドMPAは、MPAに、インタラクティブな部分だけ、Vueを埋め込んだものです。

- 昔ながらのMPAでは、JS,jQuery,CSSを直接埋め込んでいた部分を、Vite,Vue,Tailwind,TypeScriptを使って、上手にやっているだけです。

- 「ハイブリッドMPA」も、少しだけ変えて、それらしい名前を付けて、新しく見せるいつものパターンのやつです。

- 余計なAPIを減らすために、タグに初期データを埋め込むなどしています。

- この構成で、SPAとぱっと見は、ほとんど違いがわからないくらいの実装は可能でした。

- SPAと違い、認証の管理をJSでしないでよく、機能ごとに分離できるので、比較的シンプルになります。Viteのため、JSビルドが最適化されるので、初期ロードが早くなります。

- Vueを選択している理由は、メンテナンスしやすいから。Composition API + defineModelで、とりあえず、何とかなる形になったと思います。

- Tailwindを選択している理由はメリットが多いためです。CSSのクラス管理の問題がなくなる。通常のCSSより扱いやすい。Bootstrapと違い独自のデザインが作りやすい。基本パーツだけは@applyでまとめています。VSCodeのプラグインで、難易度はかなり下がります。

- コンポーネント化は、認知負荷が高くなるため、最小限。

- 基本はMPAなため、インタラクティブな部分以外なら、初学者でもなんとかなりやすいメリットもあります。一人のエンジニアで全体の管理が可能です。

- MPAのため、SPAと違い、JSが軽く、メモリリークが起きにくいため、モバイル端末でも遅くなりにくいメリットがあります。ページ遷移で、システムが最新版になります。

- SPAだとSEO対策に悩まされますが、ハイブリッドMPAだとこれがなく、さらにインタラクティブな実装も簡単にできるので、すべてのシステムで利用できます。そうなると、ハイブリッドMPAだけ覚えれば終わりなので、エンジニアにとって潰しがききます。

### フレームワーク

- Rails,Laravelが無難だと思います。

- Railsは、生産性が高い。

- PHPは、使える人が多く動かせる環境が多い。PHPの中では、Laravelが無難。

- Vite,Vue,Tailwind,TypeScriptは、どちらでも使えるので潰しがききます。

### 楽ちんで有益な方程式

```
WEBアプリケーション = MPA( Rails or Laravel ) + ( Vite,Vue,Tailwind,TypeScript )

アプリ(モバイル,PC) = WEBアプリケーション + PWA
```

### 技術バブルの方程式

```
難しこと = 価値

新しいこと = 価値

イノベーション = 新しことをすること
```

実際は、

```
有益なこと = 価値

有害なこと = 無価値

イノベーション = 潜在的なニーズを満たしたことに対する評価
```

そのため、技術バブルになると、あれれー、なんかおかしいぞーとなります。

実際には、難しくて有害な技術もあれば、簡単で有益な技術もあります。新しくて有害な技術もあれば、枯れていて有益な技術もあります。
