## 全般的な設計思想

### 基本的な想定

- ハイブリッドMPAで安く早く作る。ランニングコストも安く済ませる。

- アプリ化の要望があった時はPWAで安く済ませる。JSONとアイコンを用意するだけ。start_urlを工夫すれば、アプリっぽい初期表示も作れる。一般ユーザーにとっては、PWAもCapacitorによるアプリも違いがわからないと思います。技術的には、中身はほとんど同じ。PWAだと、アプリの更新が不要。審査も不要。手数料もない。サーバーサイドのバージョン管理をしないでいい。Capacitor,Electron,FlutterはMacじゃないと無理がありますが、PWAで済ますことでWSLだけでなんとかなるため、PCコストを安くできるメリットもあります。

- Nodeは、開発環境、WebSocketサーバーのみを想定。

- Goは、高速なWebSocketサーバーのみを想定。

- ビジネスロジックは、カテゴリーごとにディレクトリをわけたサービスクラスで整理する。シンプルだけど見通しがいい構成。DDD,クリーンアーキテクチャは、認知負荷が高くなるため使わない。そもそも、ユビキタス言語、ドメインモデルはRailsで実現できています。

- カメラ、GPSみたいなネイティブ機能は、JSで。モバイルだと加速度センサーの取得も可能。

- サービスワーカーのような管理が難しい技術は使わない。Push通知は、メール、Slackで代用。ユーザーは、そちらの通知を有効にすることで対応。WebSocketサーバーは、チャットでのみ使う。それ以外はポーリング。

- JSバリデーションがあると、JSバリデーションだけして、サーバーサイドバリデーションをしない事故を起こしやすいため使いません。APIでサーバーに投げてバリデーションをしても、UXに大差はありません。

- ゲーム関連などは別枠でUnity。この場合は、アプリでも仕方がない。

### ハイブリッドMPA

- ハイブリッドMPAは、MPAに、インタラクティブな部分だけ、Vueを埋め込んだものです。

- 昔ながらのMPAでは、JS,jQuery,CSSを直接埋め込んでいた部分を、Vite,Vue,Tailwind,TypeScriptを使って、上手にやっているだけです。

- 「ハイブリッドMPA」も、少しだけ変えて、それらしい名前を付けて、新しく見せるいつものパターンのやつです。ちなみに、昔ながらの埋め込むやり方を、アイランドアーキテクチャと言うそうです。

- 余計なAPIを減らすために、タグに初期データを埋め込むなどしています。

- この構成で、SPAとぱっと見は、ほとんど違いがわからないくらいの実装は可能でした。

- SPAと違い、認証の管理をJSでしないでよく、機能ごとに分離できるので、比較的シンプルになります。Viteのため、JSビルドが最適化されるので、初期ロードが早くなります。

- Vueを選択している理由は、メンテナンスしやすいから。Composition API + defineModelで、とりあえず、何とかなる形になったと思います。Reactは、直感的な挙動をしないうえに、構造上、実装のための実装がかさみやすいです。

- Tailwindを選択している理由はメリットが多いためです。CSSのクラス管理の問題がなくなる。通常のCSSより扱いやすい。Bootstrapと違い独自のデザインが作りやすい。基本パーツだけは@applyでまとめています。VSCodeのプラグインで、難易度はかなり下がります。

- コンポーネント化は、認知負荷が高くなるため、最小限。アトミックデザインは、認知負荷が限界を超えるので使いません。

- 基本はMPAなため、インタラクティブな部分以外なら、初学者でもなんとかなりやすいメリットもあります。一人のエンジニアで全体の管理が可能です。シンプルな機能はMPAのみで済ませて、インタラクティブな機能はVueを埋め込むことができるため、コストを最適化できます。

- MPAのため、SPAと違い、JSが軽く、メモリリークが起きにくいため、モバイル端末でも遅くなりにくいメリットがあります。ページ遷移で、システムが最新版になります。

- SPAだとSEO対策に悩まされますが、ハイブリッドMPAだとこれがなく、さらにインタラクティブな実装も簡単にできるので、すべてのシステムで利用できます。そうなると、ハイブリッドMPAだけ覚えれば終わりなので、エンジニアにとって潰しがききます。

- MPAだとトラフィックが増えそうですが実際は誤差程度です。SPAより初期JSが軽い。JS,CSS,画像はキャッシュされる。JSONは全体のデータが必要だけど、HTMLは表示される部分だけ。テキストデータはWebサーバーでGzipなどで圧縮される。HTMLは画像に比べると小さい。HTMLだと、JSON特有の、出力してはいけない情報の出力事故がないメリットもあります。

### フレームワーク

- Rails,Laravelが無難だと思います。Djangoは癖が強く、コンフリクトが起きやすく、他のFWを併用すると混乱してくるため、実務での利用はやめておいたほうが無難です。

- Railsは、生産性が高い。ただし、フロントエンドの選択は実用的ではありません。Turboは、デメリットが多いのに、現在の通信環境では恩恵が少ないため使いません。Importmapは管理が困難になるため使いません。Stimulusは潰しがきかないので使いません。Deviseは融通が効きづらいデザインパターンですが、使える人が多いため採用しています。

- PHPは、使える人が多く動かせる環境が多い。PHPの中では、Laravelが無難。Livewireは潰しがきかないので使いません。Jetstreamは特殊用途向きで設計が特殊で融通が効きずらいので、Breezeが無難です。

- Vite,Vue,Tailwind,TypeScriptは、どちらでも使えるので潰しがききます。

- ActiveAdminなどの管理画面のパッケージは、運用していくと無理が出てくるので実用的ではないため使いません。さらに、コードがそこまで減らないケースもあります。

### 楽ちんで有益な方程式

```
WEBアプリケーション = MPA( Rails or Laravel ) + ( Vite,Vue,Tailwind,TypeScript )

アプリ(モバイル,PC) = WEBアプリケーション + PWA
```

### 技術バブルの方程式

```
難しこと = 価値

簡単なこと = 無価値

新しいこと = 価値

古いこと = 無価値

イノベーション = 新しいことをすること
```

実際は、

```
有益なこと = 価値

有害なこと = 無価値

イノベーション = 潜在的なニーズを満たしたことに対する評価
```

そのため、技術バブルになると、あれれー、なんかおかしいぞーとなります。

実際には、難しくて有害な技術もあれば、簡単で有益な技術もあります。新しくて有害な技術もあれば、古くて有益な技術もあります。そして、その逆もあります。
